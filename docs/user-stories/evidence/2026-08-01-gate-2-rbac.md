## Contrat vérifié

Le serveur calcule la décision depuis le membership du site actif et une matrice versionnée
(`2026-08-01.us-g2-002.v1`). Les cinq rôles sont distingués : `admin`, `operator`, `requester`,
`approver`, `auditor`. Une route site sans action déclarée empêche le montage. Les commandes
composites sont reclassées après parsing (`/agent create`, `/agent edit`, `/agent switch`,
`/model`, `/connector status`) avant tout effet.

Les routes globales `runtime`, `setup` de transition, modèles, probe, restart, SSH et credentials
restent hors autorité des rôles site et échouent fermées avec `INSTALLATION_ADMIN_REQUIRED`. Le GET
setup et le consentement individuel restent self-service ; le changement d'étape globale est
refusé et audité. Aucun rôle `installation-admin` n'est encore livré.

## Scénario positif

- Given : cinq sessions sur `paris`, une seconde cible sur `lyon`, et des agents, threads et runs
  synthétiques.
- When : chaque rôle appelle les actions qui lui sont attribuées via `app.fetch` Hono.
- Then attendu : l'action autorisée réussit, le rôle est relu en base à la requête suivante et les
  données restent scopées au site actif.
- Résultat observé : création de rôle/agent par `admin`, création de demande par `requester`,
  approbation `once` par `approver`, annulation par `operator`, lecture d'audit par `auditor` ; le
  changement `operator → auditor` est pris en compte sans recréer la session.
- Code de sortie/ID de corrélation : code 0 ; corrélations synthétiques générées par la campagne.

## Scénarios négatifs

### Refus RBAC stable et sans effet

- Given : chaque rôle tente une action interdite, y compris corps/header `role: admin` forgé.
- When : la requête est envoyée directement à l'API Hono.
- Then attendu : même `403 SITE_PERMISSION_DENIED`, aucun lookup/mutation/effet externe et une
  entrée de ledger attribuée au rôle relu.
- Résultat observé : refus uniformes, snapshots agents/threads/messages/runs/artefacts inchangés,
  11 refus et audits attribués.
- Absence d'effet vérifiée par : snapshots SQL et doubles runtime/disque/flux.

### Auto-élévation et approbation persistante

- Given : un admin se cible lui-même ; un approver envoie `session` ou `always`.
- When : les requêtes sont envoyées avant toute résolution de ressource.
- Then attendu : `SELF_ROLE_CHANGE_FORBIDDEN` ou `PERSISTENT_APPROVAL_UNSUPPORTED`, état inchangé,
  audit présent.
- Résultat observé : trois refus audités, aucun appel Hermes ni mutation de membership/run.

### Frontière installation globale

- Given : chacun des cinq rôles site, y compris `admin`, tente les routes runtime/setup/models/
  probe/restart/SSH/credentials.
- When : la requête arrive au registre Hono.
- Then attendu : `INSTALLATION_ADMIN_REQUIRED` avant handler, audit `installation.access`, zéro
  écriture runtime/setup.
- Résultat observé : 12 méthodes d'installation refusées pour requester/operator/admin, plus PUT
  runtime pour les cinq rôles ; snapshots runtime/setup inchangés. Le consentement individuel
  `/api/setup` reste à 200.

## Incidents, écarts et dérogations

- Une race de readiness PostgreSQL a été détectée par le contre-audit : `pg_isready` pouvait
  répondre pendant le serveur temporaire d'initialisation. Le test attend désormais le marqueur
  `PostgreSQL init process complete; ready for start up.` et une readiness finale ; deux exécutions
  consécutives sont vertes.
- `audit.export` est réservé à `admin`/`auditor` dans la matrice mais aucun endpoint d'export n'est
  livré dans ce lot.
- Le requester est volontairement limité à `thread.create` jusqu'à US-G2-003 ; il ne peut pas
  encore relire son travail via une lecture site-wide.
- Aucune P-E2E navigateur multi-compte n'est livrée dans ce lot ; la preuve API/Hono n'emporte pas
  l'acceptation produit.
- La story reste `IMPLÉMENTÉE`, sans décision de Gate et sans acceptation PO/sécurité.
